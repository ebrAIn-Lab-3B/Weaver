# Rule-based diagnosis and status repair design

Status: implementation in progress. Scope: REQ-024, TASK-133 and TASK-136; the design below also supplies the relevant state and recovery decisions for TASK-131. It does not complete TASK-131's task-creation identity work or TASK-137's evidence work.

## Observations

`findMismatches` compares task links with a Project snapshot; `reconcile` plans writes and `executeActions` requires per-action confirmation. Project item pages are paginated, but Issue labels and PR references currently have fixed nested limits. The status comparison uses a fixed column-to-board map and the reconcile action calls `setBoardStatus`, which targets every Project containing the Issue. Process read failures fall back to defaults for some callers. These facts are not sufficient to infer absence or safely update a particular Project.

## Contract

1. Identify the Project by owner and number, the Issue by normalized repository-qualified URL and the item by GitHub item ID. Shared Issue references are observations for review, never proof of an error. A GitHub add for the same Issue and Project is idempotent, but an unknown lookup or response is not proof of absence.
2. Track whether each required source is complete, unavailable or incomplete. Project item page failures fail the read; nested labels and PR connections carry independent completeness. Missing evidence or a hidden/unreadable Issue is unknown, never evidence of absence. Fail closed on an invalid or failed process read. Show the source, reason and next read needed.
3. For label-sourced columns, the authoritative label determines the column. A declared column-to-Project Status projection selects the exact Status option; absent declaration retains the current fixed projection as an explicitly identified legacy default for compatibility. It is not a claim that similarly named options are equivalent. The projection must be unambiguous and the exact option must exist. For board-sourced columns the configured board mapping determines the column, and Issue labels are not silently rewritten. An unset authoritative status requires a decision rather than an inferred transition.
4. Present source, observed values, mapping origin and Project options. Preserve DEC-012: a board ahead of its label is report-only; no automatic rollback or authoritative-state update. An unmapped or unorderable current value requires a decision, not a default rank. No status repair may infer Verified, close or reopen an Issue, or manufacture evidence.
5. Approval binds exact Project, Issue, prior values, intended values and configuration. Before each write re-read the process and selected Project item and options; refuse changed or incomplete observations. Write only to the selected Project item. Project automations or other actors may also change an Issue after a Project update. The post-read detects a changed Issue state or labels but cannot undo or prevent external side effects. GitHub does not expose a conditional atomic compare-and-set for this field: a concurrent change between the final read and mutation remains a residual race and must be disclosed, not claimed impossible. After a write, read the same scope and report success only when the intended result is observed; an unavailable or failed read leaves an uncertain result with a retry path. Repeated repairs re-read and are no-ops when already aligned.
6. Report before/after, individual outcomes and remaining warnings. Actions retain the existing per-write approval and file-PR rules. The procedure is deterministic and does not require AI. Review of incomplete data, shared issues, or ambiguous mapping is a human decision.
7. Diagnose missing or conflicting Project Status on closed Issues from their actual status label, not the Review column used for display while verification is outstanding. Report these findings for a person to review Issue state, evidence and Project automation; do not offer a Project Status write for a closed Issue through reconciliation.

## Verification matrix

Exercise both column sources; custom and legacy mappings; actual options named Backlog and Todo; missing and ambiguous mappings; absent status; ahead and behind states; closed Issues; multiple Projects; shared Issue references; incomplete labels/PR pages; failed reads and denied access; changed process or item after approval; cancellation; mutation failure and uncertain post-read; idempotent reruns; and English/Korean notices. In addition to automated tests, observe a controlled end-to-end path and record the exact exercised scope and any limitations. No real Issue should be closed or marked Verified as a side effect of this work.

## Implementation progress and remaining checks

The current worktree adds an explicit `columns.projection`, retains the legacy map when it is absent, reports shared Issues and incomplete reads, and directs status changes to the selected Project item after a fresh process/Project read. A failed post-write read is an uncertain outcome. Closed Issues are reported for evidence review instead of being proposed for Verified solely because they are closed. A Project-only lookup no longer creates a new Issue when an unlinked task has no unique matching card. The CLI emits observed Project options and process context and rechecks the same scope after an attempted action. The Overview exposes options and mappings and does not claim all checks passed when a source was skipped.

Automated checks in the worktree include compilation, a stateful mock CLI approval/write/recheck/retry flow, shared-Issue and custom-mapping checks, truncated label checks and selected-Project write tests. A live read-only CLI check read the selected ebrAIn.lab Kanban and its options. These checks alone do not prove complete coverage. Before completion, exercise denied and changed reads, uncertain writes, both source modes and board-ahead decisions end to end; verify actual UI and controlled Project behavior; review the remaining ACs and update the tasks with precise evidence.

On 2026-11-28, with user approval, a new disposable [Issue #86](https://github.com/blcktgr73/poc-sandbox/issues/86) and temporary Project #6 were used for a board-status-source check. The new Project had six enabled workflows, including automatic Issue closing; the Issue initially had no Project membership. Weaver planned its addition to Project #6. The add was sent, but immediate verification failed and the same-run recheck reported it absent; a later GitHub read showed exactly one item with `Todo`, and a fresh Weaver run proposed no duplicate. The cause of the initial discrepancy is unconfirmed. Clearing the temporary item's Status produced a `status-source-needs-decision` report with no write action; setting it to `Todo` and rereading removed that warning, while the Issue stayed open. The disposable Issue was then closed as not planned, its temporary Project status changed to `Done`, and Project #6 was deleted. A final read showed the Issue closed with no Project membership and PALab Ops remained the only user Project. The Issue's creation and closure history remains public. The CLI now marks a recheck incomplete after an action failure, because a single snapshot cannot settle an uncertain write; targeted tests reproduce the delayed-observation scenario without asserting its cause.

Project item pagination is not an atomic snapshot. The reader now rejects a missing or repeated cursor and a change in Project title or Status options across pages, but GitHub can still add or remove items between pages without exposing a snapshot revision. A complete pagination response therefore cannot prove a globally consistent point-in-time inventory under concurrent edits. Writes remain scoped and are reread, and this remaining limitation must not be described as atomic exclusion.
