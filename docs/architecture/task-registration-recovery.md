# Task registration identity and recovery investigation

Status: design and implementation in progress for REQ-024, TASK-131 and TASK-132. This document describes the implemented protections and the remaining limits of the candidate safety contract.

## Observed boundaries

The CLI includes paginated repository Issue and PR inventories in number allocation, rejects a matching task-title candidate, and repeats the Issue inventory immediately before Issue creation. Failed or incomplete pages fail closed; each inventory has a 50-page ceiling. These reads are not an atomic snapshot or a lock and do not exclude external writers. A later process may explicitly supply a known Issue URL through the limited `--resume-issue` path described in TASK-132; one verified open PR can be reported as pending, and a verified pushed branch without a PR can be offered for a separately approved PR. Unknown outcomes still require investigation. The VS Code authoring workflow drafts files and opens a PR; it does not make an Issue and Project membership part of an atomic transaction. Reconcile can link a task to a unique matching Project card, but cannot establish the absence of an Issue outside the Project. The action executor requests approval per write and stops after failure; its log is not a transaction journal and a successful log entry alone is not an authoritative GitHub read.

These observations follow `packages/cli/src/taskCreate.ts`, `run.ts`, `actions.ts`, `reconcileFiles.ts`, `filesPullRequest.ts`, and `apps/vscode-extension/src/makeTaskFile.ts`. The partial-write fixture in `packages/cli/test/run.test.ts` observes an Issue and card write followed by a failed file-branch push; it does not simulate a second process or establish absence of a duplicate. The Project reads and limits are documented in [the reconciliation design](task-reconciliation-design.md). The HealthBridge incident and issue links are recorded in [REQ-024](../requirements/REQ-024-task-registration-recovery.md).

## Candidate identity and coordination contract

1. The candidate contract calls for a stable registration operation identifier with an immutable intent. The current implementation derives a conservative operation key from the repository, requirement identity and normalized title; it does not yet persist an immutable intent manifest. A canonical repository-qualified task ID is a separate identity: a title, label, Project card or search hit is not a unique key. Creation exposes the operation and task reservation refs before asking for approval. An explicit resume requires the operator to confirm that the task details match the original intent.
2. Cooperating creators need an atomic, repository-visible reservation of both operation ID and task ID before Issue creation. A local lock does not coordinate machines; a read followed by Issue creation is not atomic. The current implementation creates two permanent Git refs, one keyed by a hash of repository, requirement identity and normalized title and the other by task ID, pointing at the observed default-branch commit. It does not yet store a versioned immutable intent manifest. A failed or unknown response aborts without retrying or deleting any ref; an abandoned reservation needs investigation, and deletion or takeover is a separate explicit decision, not an automatic timeout. GitHub ref creation, repository permissions, branch rules and retained refs are external dependencies and must be verified on the target host.
3. Only the execution that receives confirmed creation of both new refs may call Issue creation; an existing or uncertain ref is never adopted by another creator. With cooperating executions and no external ref removal this excludes a second creator with the same operation key or task ID, including while the first is paused. It does not fence actors that bypass Weaver or delete the reservation, and a reservation alone is not an exclusive lease for later recovery steps. GitHub Issue creation does not offer an idempotency key or an atomic conditional create tied to a Git ref. An interrupted or concurrent Issue-creation attempt therefore stops for human investigation; a search result or elapsed timeout must not be treated as proof that another writer cannot still create an Issue. Initial file-PR creation and branch-without-PR recovery now acquire the same persistent PR reservation, so cooperating attempts cannot both create a PR. A failed or unknown result retains the reservation and may require human investigation; other concurrent recovery and external writers remain limitations.
4. New Issues carry a versioned operation marker and task ID in the body. Read the Issue directly when its URL is known; when it is not, complete repository-wide reads report matching title candidates and whether each marker matches. The caller must establish that the prior creator has stopped and explicitly choose a URL; the marker is not automatic adoption. Search indexing and list reads can lag, Project membership is not an Issue inventory, and a 404 may mean inaccessible. A unique matching marker helps locate an Issue but cannot by itself prove no in-flight creator exists. Multiple candidates, mismatched intent, shared task/Issue associations or incomplete access remain unresolved with the affected source and an explicit decision path. Never split or relink a shared Issue automatically.
5. Record a write as confirmed only after a fresh authoritative read verifies its identity and intended effect. An interrupted request, timeout, invalid response, failed post-read or disagreement is `unavailable`/uncertain, with known IDs retained. Do not infer absence from one stale read. Project item addition is idempotent for an Issue in one Project, but a read can lag; retain the uncertainty and reread before retry. For Status and labels, do not overwrite an already valid different state to force an initial state. For PRs, inspect the exact branch and its PR, including closed and merged states; a branch pushed before a failed PR request is not evidence that no PR exists. Verify merged task and requirement files separately from a proposed PR.
6. Every write retains DEC-008 approval. Approval binds identity, repository, Project, current observed facts, exact values and effective process; reread and reject stale or incomplete facts before execution. File changes remain on a reviewed PR. A successful PR creation is pending until the default-branch files and links are observed. Per-step machine and human output must preserve identifiers, evidence source, status, cause and next action; one failed or unavailable step prevents an overall complete result.

## Alternatives and open decisions

An unrestricted title search was rejected as identity because titles are neither unique nor stable. The current hashed operation key is a conservative coordination key, not proof of task identity; two semantically identical requests with different titles need not share it. A local-only journal can preserve IDs on one host but cannot exclude another host or survive loss of the journal. A global hosted lock service would add an infrastructure dependency and needs durable fencing accepted by the GitHub mutation; a time-based lease without such fencing cannot prevent a paused former holder from writing. Repository refs reserve names atomically but cannot make subsequent Issue creation atomic. A manual, fail-closed handoff is safe only when the human can establish that no prior executor can still write; if that cannot be established, the state stays unresolved. The recovery protocol, intent manifest and cleanup UX remain open work.

## Investigating retained reservations

Record the operation, task and PR reservation refs and all returned Issue, Project item, branch and PR identifiers. Refs coordinate cooperating executions; they are not a transaction journal and may reflect only part of an attempt. Stop every previously authorized executor and check for paused or queued jobs and collaborators before considering recovery. If an executor might still write, leave the reservations in place and keep the outcome unresolved; elapsed time and an empty search do not establish that it has stopped.

Inspect the exact refs and a complete repository Issue inventory, candidate markers and repository-qualified Issue identities, Project membership and fields, the branch and all associated PR states, and any merged files. Check the intended requirement and task details against the original request. Failed, incomplete, hidden or potentially stale reads remain unresolved; a 404 does not prove absence. A marker helps identify a candidate but does not establish exclusive ownership or resolve a shared Issue. Preserve existing valid status and field values rather than resetting them to an initial value.

Once the prior executor is known to have stopped and one Issue is verified, an operator can explicitly choose its URL with `--resume-issue` and review each proposed action. If no Issue can be established, do not automatically retry or remove a ref. Any cleanup or takeover is a separate human decision after investigation, limited to the exact affected refs; record the decision and evidence in the repository task or PR. Never remove a reservation while an earlier executor may still run, and do not bulk-delete reservations. Weaver has no automatic cleanup or atomic compare-and-delete protocol, and privileged external ref deletion cannot fence an earlier executor.

## Verification matrix

Exercise both column sources with custom initial columns and mappings; unavailable and malformed process, Issue, Project, PR and file reads; no, one and multiple identity candidates; shared Issues; partial/unknown outcomes immediately before and after every mutation; stale and changed observations; existing valid state and Project automation; open, closed and merged PRs and an already-pushed branch; repeated runs; simultaneous creators and a paused former executor; declined approval; and both message catalogs. Test source coverage independently of pagination and demonstrate that truncated pages fail closed. Run synthetic partial-failure fixtures and, once the protocol is implemented, an isolated disposable Issue and Project with automation inspected. Document residual non-atomic reads and the inability to guarantee exclusion against actors that bypass Weaver. Unit tests alone do not establish the complete live flow.
