# DEC-027: Markdown viewing and human authoring

- Status: proposed; awaiting human review
- Date: 2026-11-18
- Related: `REQ-021`, `REQ-022`, `TASK-115`

## Context

People need to read ordinary Markdown and diagrams and author ideation and requirement documents without an agent. Files in the repository remain the source of truth. Existing users can choose the text editor and the Requirement view remains available.

## Proposed first slice

1. Ordinary Markdown and task files open in a Weaver rendered editor by default, with an action to open their source. A task also offers an action to open its requirement at that task. Requirement documents retain their existing view. Weaver contributes a bundled Mermaid renderer to this view and VS Code's Markdown preview; valid Mermaid fences render as diagrams and an invalid fence remains visible with an explanation. The renderer runs locally. Other diagram formats are not promised in this slice.
2. The commands for creating an ideation or requirement file ask for the destination and show the initial content before creating it. Ideation begins with only the chosen title. A requirement starts with the required schema fields, outcome, and one acceptance criterion. Both remain ordinary Markdown.
3. The initial requirement ID proposal follows the largest existing parsed requirement ID in the workspace. After preview, cooperating local Weaver processes using the same temporary directory serialize the final workspace recheck and exclusive destination creation using a lock directory. A competing creator fails and can retry; a changed proposal requires a new preview. A process interrupted while holding the lock can leave it behind: after confirming no Weaver creation is running, remove the lock directory shown in the message. The lock does not coordinate independent writers, other temporary directories or other machines, and cannot guarantee uniqueness across workspaces whose scans do not see the same files. Exclusive creation also prevents overwriting a destination.
4. A requirement can link to an ideation file in the same workspace folder with an ordinary relative Markdown link, inserted as an unsaved text edit.
5. The initial view edits a single-line heading or paragraph as a targeted Markdown text edit. The subsequent product direction for a Notion-like block editor and slash commands is recorded in [DEC-028](./DEC-028-notion-like-markdown-editing.md). Source mode remains available.

## Review and limitations

On 2026-11-20 the maintainer selected the repository as a common allocation scope for nested workspaces and chose a repository allocation history. The proposal and protected recheck scan the workspace, and, for each local workspace folder inside a Git checkout, also scan Markdown and allocation history under the nearest enclosing checkout, including files outside a nested workspace folder. The repository scan does not follow symbolic links and skips `.git`, `node_modules`, `dist`, `out`, `examples`, and `.claude/worktrees`, matching the existing workspace exclusions. Folders without an enclosing checkout use their workspace scan and folder history. The lock still requires the same temporary directory and cooperating processes. Repository scope alone does not guarantee uniqueness across differently composed multi-repository workspaces or disconnected copies.

After confirmation and the protected recheck, Weaver appends the ID to `.weaver/requirement-ids.txt` in the checkout root (or selected folder when no checkout exists), flushes it, and then exclusively creates the document. Commit and preserve this file; each line is a reserved `REQ-###` ID. A failure after reservation consumes the ID, including a destination collision. Cancellation before confirmation does not reserve one. An empty, incomplete or invalid existing history stops creation until the history is reviewed and repaired; do not delete entries merely because a document was removed. A missing file is treated as a first use, so Weaver cannot distinguish that case from a deleted history file. Existing files contribute to the proposal, but IDs deleted before history existed cannot be inferred from current files. Bootstrap those from trusted historical records when needed. Separate clones and nonparticipating writers can still allocate the same ID and require reconciliation. These limitations leave the schema's broader workspace uniqueness and historical never-reuse guarantees unresolved.

Human review should confirm the initial Mermaid-only support, templates, and ID rules. Compatibility with other Mermaid extensions, preview security settings, live editing, and source preservation must be checked in the extension host. No task or requirement is verified by this proposal alone.

## Repository-qualified identifiers decision (2026-11-21)

The maintainer selected `owner/repository` as the repository identifier and a requirement ID local to that repository. No separate repository ID or shared cross-repository allocation history is required. Weaver must distinguish requirements by repository and requirement ID when combining repositories; within a repository, its existing local history remains the allocation record. The same `REQ-###` may occur in different repositories. An `owner/repository` name does not distinguish repositories with the same name on different Git servers; the maintainer accepts that limitation for now. Renames and transfers require references or an explicitly configured alias to be reconciled; automatic identity across renames is not established.

The creation proposal and locked recheck use the selected checkout and its history, excluding nested checkouts. A folder outside Git uses its selected folder as the local allocation domain. In the VS Code workspace, a checkout's local path identifies its files; when possible, the `origin` Git configuration provides `owner/repository` without a network request. Tasks can specify `requirement_repository` for a cross-repository reference; otherwise a local match is preferred, and a legacy reference without a local match resolves only when it is unambiguous. The schema and consumers use these identities when available. Files read without checkout context and without repository metadata remain ambiguous rather than being assigned a guessed repository. The history-file loss, historical bootstrap, independent-clone and nonparticipating-writer limitations above remain; the decision does not establish global uniqueness or unconditional never-reuse. The earlier workspace-wide allocation description records the superseded implementation.

## Git server qualification (2026-11-21)

The maintainer chose a portable reference using the Git server host and `owner/repository` where names conflict across servers. Existing unqualified references remain valid when unambiguous; local folder names and paths are for local selection, not identifiers written into cross-repository references. A task may use `requirement_server` together with `requirement_repository`. `repository_server` records a document's repository host when needed; a local checkout may supply its host from the Git `origin` without a network request. Compare host names without case and do not retain credentials, transport scheme or port. Distinct services on the same host cannot be distinguished by this scheme. A server-qualified reference does not match a target with an unknown server, and an ambiguous unqualified reference is not resolved by choosing the first match. Repository or server moves require references to be reconciled; automatic migration is not promised. This does not implement or verify DEC-030's optional shared allocation domain.

## Server address decision (2026-11-21)

The maintainer chose a Git server address rather than a host name alone. Use a host name or IP address and an optional explicit port to distinguish servers on the same host. Local paths remain local selection information; credentials are never part of the identity. Preserve backward compatibility for existing host-only references, and do not silently equate different addresses or ports without an explicit mapping. Different DNS aliases, an IP address and a host name, or SSH and HTTPS endpoints may refer to the same service but are not automatically known to be equivalent. Services sharing the same address and port but distinguished only by URL path remain outside this identity model; moves and renames still require reconciliation. These are accepted limitations, not claims of global uniqueness.

This decision supersedes the host-only and no-port statements in the preceding section. The implementation normalizes host-name case, IPv6 representations and numeric ports. It retains explicitly supplied ports, including protocol defaults, and treats an omitted port as distinct from an explicit one; it does not assume that SSH and HTTPS ports identify the same service. Existing host-only references remain valid, but a reference without a port does not match an origin that explicitly includes one. The decision does not establish offline host behavior or implement DEC-030.

DEC-030 was subsequently withdrawn and TASK-128 cancelled; shared-root allocation and its proposed change to root discovery are not pending implementation.

## Creation confirmation paths (2026-11-21)

Creation confirmation displays the destination and, for requirements, the allocation-history path in its detailed preview alongside the initial content. Paths are explicitly broken across lines so the Windows native dialog does not abbreviate the middle of the tested long paths; joining the displayed lines reconstructs the path. The requirement confirmation still warns that an ID may remain reserved after failed creation. See TASK-118 for the actual UI check and its limits.

## Local creation verification scope (2026-11-21)

The maintainer chose to conclude the local-creation review using the recorded evidence that the exercised creation paths work without an agent, board or GitHub, including the real local VS Code UI checks and the simulated-dialog harness that rejects common Node networking entry points. A physically network-disconnected VS Code host is not a prerequisite for completing TASK-118 under this scope. That host was not tested: the evidence does not prove every network entry point is blocked or that every VS Code host works while disconnected. Investigate a concrete offline failure separately if one is found. This scope decision does not change the local-first product intent, establish remote-provider behavior, or waive DEC-006 closing-PR evidence.
