# Create tasks with configured initial state and resumable steps

## Dependencies

TASK-131 design and decisions.

## Acceptance criteria

- Implement the agreed creation and recovery path for requirement entry, task file PR, Issue, Project membership and initial state using the target repository process; expose per-step outcomes and identifiers.
- Resume after failure or unknown result without repeating confirmed work; fail closed on ambiguous identity or incomplete reads, including concurrent attempts. Preserve configured task fields, approval and file PR rules.
- Test labels and board-status with custom mappings, missing or ambiguous mappings, every write boundary, reruns, concurrency and access failures; catalog user-visible messages in English and Korean.

## Tests and completion evidence

Linked implementation PR and passing targeted automated tests with partial-failure and retry results; record remaining concurrency or host limitations.

Status: in progress. The implementation and observations below are not yet complete or independently reviewed.

When an Issue creation, Project addition or Project field call fails without a confirmed result, the action reports the underlying error together with a localized instruction to inspect the relevant reservation, Issue or Project item before resuming. An Issue creation failure explicitly warns against creating another Issue while its outcome is unknown. Fixtures exercise these messages and Korean Project-add guidance; a failed request is conservatively treated as uncertain even when the host may have rejected it before writing.

The same conservative guidance now covers an uncertain file-branch push or PR creation. A fault-injection fixture creates a PR from an already verified branch but loses the response; the next read-only resume verifies the existing PR and its files, reports it as pending and makes no second PR request. If the PR remains hidden from the following reads, another fixture confirms that the retained reservation refuses a second PR attempt. These exercise the recovered-branch path with a mock host, not every possible concurrent GitHub actor.

## Work in progress (2026-11-28 KST)

The CLI rejects an unreadable or invalid target process and an ambiguous initial state before planning writes. `columns.initial` selects the initial column (default Backlog). Label-sourced creation uses its configured label; board-status creation plans a separately approved Status write only for a unique mapping to an actual option, reads the item before and after, and refuses to overwrite a different value. `npm run check` and the CLI tests exercised these paths with mocks, including denied process reads. These changes do not provide resumable identity, concurrent exclusion, complete post-write verification, or complete registration; rerunning creation after an uncertain write can still create another Issue. The board Status read and write are not atomic. Do not treat this work as task completion.

Action results now carry known task, Issue, Project-item, branch and PR identifiers where available, including the task identity when a write fails. A successfully opened file PR returns overall `pending` and exit code 4, rather than asserting that registration is complete; this does not verify the PR contents or merged files. The remaining recovery and concurrency work is unchanged.

Creation now reads the target repository's paginated Issue and PR lists, rejects a matching task-title candidate, and repeats the Issue read before Issue creation. It refuses failed or incomplete reads and stops at a 50-page ceiling. It also re-reads the target process before each write and stops when the process changes or becomes unreadable. Mock tests cover an Issue outside the Project, an intervening Issue, changed process, failed reads and pagination. A title candidate is a warning requiring investigation, not a unique identity or automatic association. These reads cannot exclude a concurrent write between the last read and mutation.

The CLI has a limited `--resume-issue` path for a known Issue produced by the current creation format. It checks repository-qualified identity, title, requirement/path body, repository inventory, configured status, existing Project item, task artifacts and PRs. It reuses an existing card or adds and rereads a missing one, then offers the file PR with separate approval. A matching pushed branch can be verified and used to propose a PR; conflicting task files, ambiguous PRs, shared associations and unreadable data stop the path for investigation. It does not automatically adopt candidates from unknown Issue outcomes or fence actors that bypass its recovery reservation.

Resume results include a timestamped observation of the Issue, Project membership and status, while explicitly marking files unverified. Creation approval IDs now bind task criteria, assignee, effective process, Project and the rest of the intended inputs; a fixture confirms an approval cannot be reused after changing the assignee. The status observations remain subject to the non-atomic reads described above.

Before Issue creation, the approved action creates persistent Git refs for the operation key and task ID. Only the execution that receives successful responses for both may create the Issue; failures and uncertain responses stop without cleanup or automatic takeover. Mock tests cover simultaneous reservations, a lost response and different operations claiming one task ID. This guards cooperating creators using the same operation key or task ID while refs remain intact; it does not fence external writers or concurrent recovery. Repository write permission and compatible branch rules are required. Retained or partially created refs need explicit investigation; deleting them while an executor may still run would defeat the protection.

On 2026-11-28 KST, two concurrent calls to the compiled reservation helper used newly named disposable refs in `blcktgr73/poc-sandbox`: one succeeded and one was rejected. Both exact probe refs were read and deleted after the calls ended, and subsequent reads returned 404. No Issue or Project write was performed. The first live attempt failed before creating either ref because Node Fetch rejected a GET body; the code was corrected and Fetch request-construction tests were added. A separate live read of the Issue and PR inventories returned 46 Issues and 40 PRs in the sandbox and 143 Issues and 272 PRs in Weaver. These observations verify the exercised helper calls and cleanup, not the full CLI transaction, uncertain GitHub response recovery, or exclusion of non-Weaver actors.

The creation action now rereads the returned Issue and verifies its identity, title, body and expected labels before proceeding. Project addition also requires a fresh read confirming the returned item and Issue in the selected Project. If either post-read fails or disagrees, the action stops and retains any returned Issue URL or item ID in the result. Fixtures cover inaccessible or changed Issue reads and an addition missing from the subsequent Project read. These observations are not atomic, and a failed verification remains uncertain rather than proof that the write did not occur.

After a file PR is opened, the CLI rereads its URL, open state and head branch before reporting it as pending. A failed post-read retains the returned URL and reports a failed action; it does not prove the PR is absent. The check does not verify PR file contents or a merged default branch.
